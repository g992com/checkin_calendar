# 代码质量评估（中文）

## 何时使用

当用户希望评估“本次代码交付质量”（而非模型通用能力）时使用本 Skill，典型关键词：

- 代码质量评估
- 测试结果转评估
- 根据与 `main` 分支对比的 diff 和回归结果打分
- 评估是否可发布/可合并

## 非适用场景

以下场景不要使用本 Skill，改用通用模型评测流程：

- 整体满意度、指令遵循、边界感、修复成本等模型维度打分
- 评审“评测流程是否专业”而非“被评代码是否达标”
- 仅做测试执行记录，不需要质量评分

## 输入契约（缺失则降级）

评估前先明确输入材料：

1. 需求与验收口径（Issue、任务说明、验收标准）
2. 测试结果（自动化/手测结论、失败现象）
3. 关键代码证据（git diff、关键文件片段）
4. 可选基线（历史测试或上一版评估）

其中代码证据默认以 `main...HEAD` 对比口径为准；若使用其他基线，需在报告中明确说明。

若 2 或 3 缺失，不得给高分，必须写“证据不足，待补充验证”。

## 执行流程

1. 抽取目标缺陷与业务规则，形成“验收检查点”。
2. 对照测试结果判断是否闭环（主流程、边界、回归）。
3. 对照关键 diff 判断实现范围是否与规则一致。
4. 用 6 维代码质量口径评分并给综合分。
5. 输出可执行改进项与发布建议（分场景）。

## 固定输出模板（必须同构）

按以下结构输出，不得缺段：

1. `# 代码质量评估：<模型名>（编程智能体产出）`
2. YAML `meta`（model、evaluated_at、evidence）
3. `## 1. 总评（面向管理者 / 智能体路由）`
4. `## 2. 维度评分（1–5，5最高）`（6 维表格 + 综合分）
5. `## 3. 优点（智能体值得保留的做法）`
6. `## 4. 不足与改进指令（给下一轮智能体）`
7. `## 5. 是否推荐用于生产`
8. 边界声明（一句话）

### 维度表固定字段

表头固定为：`维度 | 得分 | 说明`

维度固定为：

- 问题定位准确性
- 业务规则一致性（跨页面/跨入口）
- 前后端一致性
- 需求覆盖完整性
- 可维护性
- 回归风险（副作用）

并在表格后给：`综合：X.X / 5`。

## 评分说明（简版）

评分采用固定 6 维，完整 1–5 分档位与证据映射以 [`reference.md`](reference.md) 为唯一准据。

- 问题定位准确性：是否命中根因而非仅修表象。
- 业务规则一致性（跨页面/跨入口）：同一规则是否在各入口一致生效。
- 前后端一致性：接口语义、状态流与 UI 行为是否一致。
- 需求覆盖完整性：主流程与关键边界是否闭环。
- 可维护性：实现是否清晰、可复用、易于后续演进。
- 回归风险（副作用）：是否存在可复现副作用与发布风险。

## 降级策略（证据不足时）

- 缺测试结果：最高不超过 3 分，标注“待回归验证”
- 缺关键 diff：最高不超过 3 分，标注“待代码复核”
- 同时缺测试与 diff：仅输出“阶段性评估”，不输出发布通过结论
- 结论冲突时：优先可复核日志与代码证据，冲突点单列说明

## 输出前自检清单

发布评估前逐条核对：

1. 是否严格使用 8 段固定结构
2. 是否只使用 6 个代码质量维度
3. 每个维度是否都给出证据性说明
4. 是否给出 `综合：X.X / 5`
5. 是否包含可执行改进项（改哪里 + 如何验收）
6. 是否包含分场景的生产建议
7. 是否包含边界声明

## 输出落盘约定

- 目录：`.cursor/模型评估/<模型标识>/代码质量评估结果/`
- 文件名：`评估结果_<模型标识>+<YYYY-MM-DD-HHmm>.md`
- 若用户明确要求仅对话展示，可不落盘
