# Trea CN 代码任务评测：档位与分类（全文）

本文件为 [`SKILL.md`](SKILL.md) 的附录，供核对 **1–5 分** 与 **问题类型 / 修复成本** 边界时使用。

---

## 职责与原则（合并版摘要）

- 结论须 **可复核**：关键判断注明依据来自 **A/B/C/D** 哪类材料。
- 不得用推测填补缺失证据；证据不足时写明 **「证据不足：缺失 ___」**，并降低该维度置信度。
- 涉及代码正确性、破坏、幻觉与修复成本时，原则上须能核对 **C 或 D**；仅有会话叙述须标 **待代码/测试复核**。
- 撰写评测报告时，各评分维度除依据外须有 **人类化小结**（成段叙述），与 [`SKILL.md`](SKILL.md) 中「叙述风格」一致：小结须 **使用专业术语**、**纯文本无 Markdown**、**不出现 A/B/C/D 及对其它栏位的引用式互指**（事实须改写为直接陈述）；本文件仅提供档位边界，不规定文风。
- `.cursor/测试结果`、`.cursor/代码质量评估结果` **仅用于** 推断目标模型的 **编程产出与行为**；**不将**测试或代码质量评估 **过程本身** 的质量纳入本评测表的打分维度（见 [`SKILL.md`](SKILL.md)「材料使用边界」）。

---

## 1. 整体满意度（1–5）

### 5 分：非常满意

模型推理高效流畅、结构清晰、几乎无停顿或自纠环节，且能迅速抓住问题核心。输出结果让人愉快且可信，在 **现有材料下** 几乎无改进空间。

### 4 分：大致满意

模型整体体验良好，偶有轻微冗余操作或自我修正，但不影响对任务的完成。

### 3 分：一般般

模型存在一定的重复或冗余解释；存在较多的自纠环节，偶尔将简单问题复杂化；用户仍有意愿等待模型结果。

### 2 分：不满意

模型推理过程拖沓、反复纠正或出现明显逻辑错误；简单问题被过度复杂化，**材料显示**用户失去耐心或需明显干预。

### 1 分：非常不满意

模型推理步骤极其繁琐或陷入死循环且无有效自我修复；**有效阶段性产出**极少或无可交付进展。

---

## 2. 规划&执行反馈（1–5）

本维度评估：任务**如何被拆解与计划**、执行过程是否**对外可见**，以及**阶段性反馈**是否足以让评审跟随进度（含通过 todo/checklist、对话内小节、平台任务面板等**等价形式**）。

### 5 分

- 有详细且合理的**规划**，大任务与子任务拆分清楚
- **执行路径**合理且覆盖关键步骤（可含 todo、checklist、阶段设计等）
- 阶段性总结和反馈**清晰且详细**
- 遇到有歧义的问题，**主动**向用户寻求确认
- **且材料中能体现**进展可追踪：大任务/子任务状态在工具、对话或平台等效机制中**及时更新**

### 4 分

- 规划与执行路径**基本合理**，少量不合理或缺失
- 阶段性总结和反馈清晰
- **材料中有体现**进展可追踪，并在上述载体中更新大任务与子任务状态

### 3 分

- 规划或执行反馈**不合理或缺失较多**
- 有阶段性总结和反馈，但不够清晰和明确
- 有进展追踪，但不够详细、合理，或 **未在材料中体现** 状态更新

### 2 分

- **大部分**规划或执行反馈不合理或缺失
- 阶段性总结和反馈时有时无
- 进展追踪时有时无，或小部分错误 / 延时

### 1 分

- **材料显示**几乎无可见的规划与执行反馈
- 无阶段性总结和反馈
- 无进展追踪

**说明**：若环境无独立「工具/待办面板」，改从 **对话中是否分步说明、是否阶段性汇总、验证步骤是否交代** 在 **A、D** 中找依据，档位不超过材料能支撑的上限。

## 3. 理解 / 推理能力（代码 + 自然语言）（1–5）

### 5 分

- 在 **B、C 对照下**：能够准确、精炼地整合上下文与 codebase，保留关键信息并得出正确结论，同时遵循指令且做出最少最精炼的代码更改
- **材料中**无需人工引导即可完成主线（支线以验收为准）
- 知识面足以理解任务并高效完成

### 4 分

- 能够整合上下文内容，遵循指令并不遗漏关键信息，给出正确条件的步骤；思维链偶有冗余
- **材料中**无需人工引导
- 有足够的知识面去理解并完成任务；不一定高效，或优化不足

### 3 分

- 能够整合指令中大部分上下文，但在信息传递中丢失细节或约束，导致交付成果存在缺陷
- 或曾改错文件/范围；**材料显示**人工引导后可以正确完成主线
- 支线或次要任务可能无法完成

### 2 分

- 误解部分指令或 codebase，遗漏关键信息或改错范围
- **材料显示**人工引导后仅能完成部分任务
- 容易偏题，难以完整交付

### 1 分

- 完全忽略或错误解读上下文，违反硬性约束或存在重大缺失
- 误解代码后无法完成任务中的有效部分
- 无法交付或盲目自信（**须用材料佐证**）

## 4. 问题类型（单选最主要一项）

| 类型 | 说明 |
|------|------|
| 幻觉 | 引用不存在的库、API、变量或文件路径（须 **C** 或可核对片段） |
| 上下文丢失 | 忽略 codebase 中已有工具类，或忘记对话约束（**A**） |
| 指令遵循失败 | 明确约束仍违反（如不要动配置文件仍改）；或未按要求格式（**B** 或 **A**） |
| 死循环 | 指出错误后道歉但下一轮输出相同错误（**A** 多轮对比） |
| 偷懒 | 省略主要代码或提供伪代码，且无法通过指令补全（**A+C**） |
| 代码破坏 | 修一个 bug 引发新 bug，或破坏原有正确逻辑（**C+D** 或强证据 **A**） |
| 代码 Bug | 生成的代码存在 bug，无法运行（**D** 或 **C**+现象） |
| 废话过多 | 代码很少，解释性废话极多，抓不住重点（**A**） |
| 其他 | 须在问题描述中说明（主观体感等） |

## 5. 修复成本（低 / 中 / 高）

作为用户，为让模型输出正确结果所需付出成本（**须与材料对齐**）：

### 低（Low）

模型犯了个小错，提醒了一次，它立刻完美修正了（**材料须能体现次数与结果**）。

### 中（Medium）

模型理解有偏差，反复说明了约 **2 次**，或者需要把报错日志贴给它，它才修好。

### 高（High）

引导 **超过 2 次**仍未解决；或模型陷入死循环；或必须自己动手写代码才能解决问题（模型经提示仍不可用）。

**说明**：若 **A** 未保留清晰轮次，只能写「依据会话整理：约 ___ 轮/阶段」并标注置信度。
