# Trea CN 代码任务评测

## 何时使用

用户需要对 **Trea CN（或同类）平台上模型完成的代码任务** 做 **模型表现打分、问题判定、修复成本评估**，并产出 **可填入评测表** 的规范输出时，先读本 Skill，再按需打开 [`reference.md`](reference.md) 核对 **1–5 分档位全文**。

## 输入材料（先列清单再打分）

评测前在输出中列出本次实际使用的材料（勾选/路径/「未提供」）：

| 代号 | 内容 | 用途 |
|------|------|------|
| **A** | 原始多轮对话、每轮归档、结构化归档、完整日志（任一或组合） | 轮次、自纠、澄清、修复过程、体感 |
| **B** | 任务说明、验收标准、测试用例说明 | 指令遵循、完成度、是否偏题 |
| **C** | git diff、关键文件片段 | Bug、破坏、最少改动、路径/API 幻觉 |
| **D** | 自动化测试、构建日志、手动测试、报错栈；以及 `.cursor/测试结果`、`.cursor/代码质量评估结果` 中 **与被评代码行为相关** 的结论摘录 | 可运行性、修复成本、现象核对 |

**证据缺口**：某类未提供时，必须在输出中写明；相应结论降级或标 **待复核**。

### 材料使用边界（测试结果与代码质量评估）

- `.cursor/测试结果`、`.cursor/代码质量评估结果` **只用于** 支撑对 **目标模型（编程智能体）** 的能力判断：例如其改动是否通过用例、是否存在缺陷、静态审查中指向的具体代码问题等。
- **不得纳入** Trea 模型评测结论的内容包括：测试报告撰写质量、用例设计是否完备、Playwright 等工具脚本好坏、评审人笔误或格式、代码质量评估流程本身是否专业——除非用户明确要求评「评测流程」而非「模型编程任务」。
- 若材料中混有对上述「过程质量」的叙述，撰写本评测报告时 **忽略其对各维度打分的影响**，仅在「证据缺口」中必要时一句说明「未评价测试/质检过程本身」即可。

### 平台仅能访问「当前一轮」时

若模型或平台 **无法** 访问完整历史，会话侧证据以 **人工维护的累计会话归档** 为准；须在「证据缺口」中说明 **未提供原始逐条对话**，并降低与轮次、死循环、修复次数相关结论的置信度。

### A 类会话材料的使用优先级（多归档并存时）

- 同一模型目录下若存在 `会话记录_*_每轮归档.md`、`会话记录_*_完整日志.md`、`会话记录_*_结构化归档.md`，默认采用：
  1) **每轮归档**：用于轮次级变更、阶段推进、当轮交付与命令；
  2) **完整日志**：用于复核关键陈述、修复次数与是否重复犯错；
  3) **结构化归档**：用于快速定位文件清单、差异主题与待核对项。
- 若三者结论冲突：以 **完整日志 + 可复核代码/测试证据（C/D）** 为最终依据，并在「证据缺口」写明冲突内容与处理口径。
- 若仅有每轮归档而无完整日志：可评，但对「死循环、反复纠偏次数、语义细节」的结论应降置信度。

## 执行顺序

1. **材料清单**：A/B/C/D 使用了哪些（路径或粘贴摘要）。
2. **证据缺口**：缺什么；哪些判断因此降级或待复核。
3. **三维度打分**（1–5）：整体满意度、规划&执行反馈、理解/推理能力（代码 + 自然语言）。各维度须有 **依据**（可条列、指向 A/B/C/D）+ **人类化小结**（见「叙述风格」）。
4. **问题类型（单选）** + **描述**（证据与分类理由）；**问题类型**同样须有 **人类化小结**（可与条列描述并存：先段落后要点，或段末收束）。
5. **修复成本**（低 / 中 / 高）+ **依据** + **人类化小结**。
6. **综合评语**（可选，≤120 字）：与前述各段小结呼应，不重复堆砌分数与标签。
7. **落盘**：按下文「输出落盘约定」将完整 Markdown 写入 `.cursor/模型评估/<模型或任务标识>/`（用户明确要求「只回复不保存」时除外）。

档位定义与细则见 [`reference.md`](reference.md)。

## 叙述风格（人类评审员）

除「材料清单」「证据缺口」可保持条列外，**每个评分维度**须让读者感觉像 **真人同事在评审会上的转述**，而非仅标签与证据堆砌。

### 小结（人类化段落）的硬性要求

以下仅约束各维度下的 **「小结」** 与 **「综合评语」** 的正文（**「依据」「描述」「与 B/C 对照」等条列字段** 仍可用 Markdown、代号、路径，以便复核）。

1. **专业用语**：优先使用与本任务相关的 **行业与技术术语**（例如：验收标准、回归测试、静态资源缓存、WebSocket 回显、边界用例、回归风险、任务拆解等——随具体项目替换），避免空泛口语替代可核对的技术含义。
2. **纯文本**：小结与综合评语正文内 **不使用任何 Markdown 标记**，包括但不限于：加粗、行内代码反引号、链接、`#` 标题、列表符号、引用块。写成连续的中文句子；如需强调，靠措辞与句序，不靠格式。
3. **禁止引用与互指**：小结内不得出现材料代号 **A/B/C/D**，不得写「与 B 中……」「在 D 支持下」「见上文依据」「如材料清单所述」等 **指向其它栏位** 的表述。若需表达同一事实，应 **先理解再概括**，用完整句子直接陈述内容（例如将「验收中的两分钟窗口与右键入口」写进句中，而不是写「与 B 中……」）。
4. **与依据一致**：小结仍须与当节 **依据** 及事实相容，但 **不复述** 依据的编号结构；读者即使不读依据也能从小结读懂结论基调。

### 小结的结构建议

- 每维度 **2–5 句**：先一句 **定调**（为何是该分/档），再 **1～3 句** 展开关键事实；可用「整体上」「主要问题在于」等衔接，但遵守上一节的纯文本与无引用规则。

### 依据（非小结）的分工

- **依据**、**与 B/C 对照**、**描述** 等：可条列、可使用 A/B/C/D、路径、加粗、代码文件名，便于复核。
- **小结**、**综合评语**：只承担 **可读叙事**，遵守「小结的硬性要求」。

### 仍应避免

- 全节只有列表无段落（指该维度整体可读性）；小结内空话（「表现良好」）且不交代实质技术判断；与 reference 档位定义 **逐字重复** 代替分析。
- **问题类型**：若 **描述** 为多 bullet，**小结** 须用一段话收束「为何归此类、是否尚存待复核」，并遵守小结硬性要求。

## 三维度（摘要）

完整 1–5 档说明见 **reference.md**；此处仅记核心轴：

- **整体满意度**：推理是否拖沓、自纠是否过多、结果是否在 **B+D** 下可信。
- **规划&执行反馈**：材料中是否体现任务拆解与计划、执行步骤是否可跟随、阶段性总结与反馈是否清晰、歧义是否主动澄清、大任务/子任务进展是否在对话或等价载体中可追踪；无记录则不得虚拟满分。
- **理解/推理能力**：**B** 与 **C** 对照是否准确、改动是否精炼；须各写一行对照结论，缺材料则声明。

## 问题类型（单选最主要一项）

判定须写明证据类型；仅有会话而无 C/D 时，对代码类标签标 **疑似，待复核**。

| 类型 | 说明 |
|------|------|
| 幻觉 | 不存在的库、API、变量、路径（须 C 或可核对片段） |
| 上下文丢失 | 忽略已有工具类/约定或对话约束（A） |
| 指令遵循失败 | 违反「不要改某类文件」、格式等（B 或 A） |
| 死循环 | 指出后仍输出相同错误（A 多轮对比） |
| 偷懒 | 主要代码缺失或长期伪代码（A+C） |
| 代码破坏 | 修 A 坏 B 或破坏原逻辑（C+D 或强证据 A） |
| 代码 Bug | 无法运行或核心路径错误（D 或 C+现象） |
| 废话过多 | 解释过多、抓不住重点（A） |
| 其他 | 须在问题描述中说明 |

## 修复成本

| 档位 | 条件（须与材料对齐） |
|------|----------------------|
| **低** | 材料显示一次明确反馈后即达标 |
| **中** | 约 2 次纠偏，或需补充报错/日志后修好 |
| **高** | 引导 >2 次仍不行；死循环；或最终需用户自行写代码闭环 |

## 输出落盘约定

- **默认目录**：`.cursor/模型评估/<模型或任务标识>/`（按模型分层；如 `.cursor/模型评估/Seed-2.0-Code/`）。
- **默认文件名**：`模型评估结果_<模型或任务标识>_<YYYY-MM-DD-HHmm>.md`  
  - `<模型或任务标识>`：与会话记录或 Trea CN 任务一致（如 `Seed-2.0-Code`）；避免空格，可用 `-` 连接。  
  - 时间戳用本地完成评测时的 **日期 + 时分**（24 小时制，如 `2026-04-08-1436`），避免同日覆盖。
- **何时写入**：用户发起「做评测 / 填评测表 / 按 Skill 输出」且 **未** 说「只要对话里显示、不要写文件」时，Agent 应使用编辑器的写入能力 **创建或更新** 上述文件，内容为「输出格式」一节的全文（可含一级标题，例如 `# 评估结果 — Seed-2.0-Code`）。
- **目录不存在时**：先创建 `.cursor/模型评估/<模型或任务标识>/`，再写入评估结果文件。
- **例外**：用户指定其他路径或仅要粘贴用时，从其指定。

## 与项目 Rule 的关系

编辑 `.cursor/模型评估/**`、`.cursor/代码质量评估结果`、`会话记录`、`测试结果` 下文稿时，会注入 [`.cursor/rules/trea-cn-code-task-evaluation.mdc`](../../rules/trea-cn-code-task-evaluation.mdc)；本 Skill 为 **完整操作说明**，Rule 为 **简短原则**。
